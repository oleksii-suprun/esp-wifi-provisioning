# ESP32-C6 Wi-Fi provisioning from Rust

This example calls Espressif's C `esp_wifi_service` component (pinned to 0.5.3) through `esp_idf_svc::sys`. The C service owns the Wi-Fi driver, connection selection, HTTP server, setup page, and profile persistence. Rust initializes it and handles the BOOT button and application loop.

## Build and run

The project targets ESP32-C6 (`riscv32imac-esp-espidf`) with ESP-IDF v6.1 and the nightly Rust toolchain specified in `rust-toolchain.toml`. It expects BOOT on GPIO9; change the pin if your board differs. The ESP Rust build environment needs `ldproxy`, `espflash`, and the Rust `rust-src` component installed.

```sh
cargo build
cargo run
```

`cargo run` uses the configured `espflash flash --monitor` runner and writes firmware to the connected board.

1. With no saved profiles, join **Hello-WiFi-Setup**, password **hello-setup-1234**.
2. Keep the connection even if your phone reports no Internet. Open **http://192.168.4.1/** if the captive portal does not open automatically.
3. Select your Wi-Fi network and submit its password. The native HTTP agent attempts the connection and saves the profile only after success.
4. Rust receives the credentials event, waits 500 ms as a browser grace period, then stops provisioning. The setup AP disappears and the application logs `Hello, Wi-Fi!` every five seconds while it has an IP address.
5. Restart the board to check that the saved network reconnects. Hold BOOT for five seconds while the application is running to reopen provisioning. This keeps existing profiles; it does not erase them.

The browser’s **End setup** button also resumes selection of saved networks. If no profiles exist, hold BOOT to reopen setup.

Closing the browser does not stop provisioning. When saved profiles exist, a setup session has a three-minute limit (`PROVISIONING_TIMEOUT` in `src/main.rs`), measured from when provisioning starts. At expiry, if profiles still exist, the setup AP closes and the native service resumes saved-network selection. Once it obtains an IP address, `Hello, Wi-Fi!` resumes. With no saved profiles, setup has no timeout. Forgetting the last profile also keeps setup open. Successfully saving credentials or explicitly ending setup still closes the portal.

## Dependency lockfiles

`Cargo.lock` records resolved Rust crates. `components_esp32c6.lock` records the resolved C components and their hashes for ESP32-C6. The latter is generated by the ESP-IDF Component Manager through `esp-idf-sys` because this project declares a remote component. Keep it in version control and let the build tools update it; do not edit it by hand.

## How the integration works

The portal assets are organized in `src/web/`:

```text
src/web/
  index.html   Page structure and form
  style.css    Layout, colors, and responsive styles
  app.js       Network selection and native API requests
```

`build.rs` bundles the CSS and JavaScript into one HTML page in Cargo's output directory. `main.rs` embeds that page and supplies it to the native HTTP agent through `web_ui`. No frontend framework, Node dependency, or separate asset server is required. Asset changes trigger a rebuild; use `cargo run` to flash them and reload the portal on the board.

The page uses `/prov/scan_result`, `/prov/status`, `/prov/profiles`, and `/prov/stop`. It supports manual network entry, password visibility, saved-network removal, and ending setup. Refresh reads the C service's scan cache; it does not trigger an immediate scan. All requests go to the board; there is no mock or preview mode.

Forget uses `POST /app/forget` in `src/portal.rs`, passing the exact SSID in a plain-text body to the native profile manager. This avoids the missing URL decoding in the component's native DELETE endpoint. The default UI in version 0.5.3 also sends an `index` parameter although the native endpoint expects `ssid`; the custom page does not use that broken path. After deletion, the page reloads profiles from the device and checks that the selected network is absent and the other networks remain. Unexpected results are shown as verification failures. The serial `Forget` log records the SSID, native result, and profile counts; it does not log passwords.

Refresh loads scans, saved profiles, and connection status independently while leaving the form usable. Responses from a refresh started before a connect, forget, or end-setup action cannot overwrite that action's state.

- `Cargo.toml` declares the managed C component under `package.metadata.esp-idf-sys.extra_components`.
- `src/wifi_bindings.h` includes the C headers used to generate Rust FFI bindings.
- NVS stores up to three profiles in namespace `hello_wifi`, using `profiles_a` and `profiles_b`.
- Unexpected errors log the failing operation and restart the chip before Rust can drop data borrowed by C. The main function never returns. This demonstration uses one restart policy instead of custom retry timers or in-process service teardown. A persistent error will therefore cause repeated restarts; use the serial log to identify it.
- The NVS storage configuration stays in a `Box` because the C storage backend borrows its address for its lifetime.
- The native service initializes networking and Wi-Fi. Do not also create an `EspWifi` instance for the same driver.
- The synchronous C event callback only updates atomics. Service operations and delays run in the main loop, outside the callback.
- For this HTTP agent in version 0.5.3, the credentials event follows connection validation, profile saving, and the HTTP response attempt. Other provisioning transports may have different event semantics.
- The HTTP agent is enabled by default by the component's Kconfig. The custom `web_ui` takes precedence over the component's default page.

## Troubleshooting and verification

Optional UI logic checks use Node's built-in test runner, with no packages to install:

```sh
node --test tests/portal.test.cjs
```

These checks use a minimal DOM and mocked HTTP responses. They cover refresh failures and races, single-profile deletion, unexpected loss of another profile, and error recovery. They do not verify browser rendering, ESP storage, or radio behavior. The reported disappearance of both saved profiles remains unconfirmed on hardware; checking the refreshed list detects that condition but does not repair its cause.

If custom `sys::esp_wifi_service_*` types are missing after changing component metadata or bindings headers, regenerate the native build and bindings:

```sh
cargo clean -p esp-idf-sys
cargo build
```

Use `std::thread` for sleeping. The crates.io package named `thread` is an unrelated code-analysis library and should not be added for this example. With esp-idf-hal 0.47, GPIO input configuration is `PinDriver::input(pin, Pull::Up)`.

On hardware, check first-time provisioning, an incorrect password (the portal should remain available), restart with saved credentials, holding BOOT to provision again, and ending setup from the browser without submitting new credentials (both with and without saved profiles). Compilation alone does not validate the radio, board wiring, or browser flow.

Also check the abandoned-setup case: connect using saved credentials, hold BOOT, close the browser without submitting anything, and wait three minutes from entering setup. Expect the timeout log followed by reconnection and `Hello, Wi-Fi!` when the saved network is available. Repeat after reopening setup to verify that each session gets a fresh timeout. With no saved profiles, or after forgetting the last one during setup, verify that the portal stays open beyond three minutes.

This demonstration uses a shared setup password and unencrypted profile records (`crypto = NULL`).
